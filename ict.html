The ICT is what the policy actually sees: an 8 × 20 matrix per frame, one row per entity, encoding every hand and object as [ type ǀ pose_in_ref (pos 3 + rot6d 6) ǀ hand_in_entity 9 ǀ flag ]. It is the bridge between the scene's geometry and a vector, so both halves are shown together and linked: the geometry on the left is exactly what the numbers on the right encode. Each entity is drawn as its actual coordinate frame, decoded from that row's own six rotation channels \u2014 solid x and y as stored, dashed z because it is recovered by cross product rather than stored. Click a cell to see what it means and light up the axis it feeds, or click an entity in the 3D view to select its row. Channels that never change across the recording are drawn dead — for cup → plate that turns out to be most of the matrix.

Tokens are built with utils/ict.py::build_ict, the standalone copy of the dataloader's _build_ict, in camera_frame mode — so the reference frame is cam0, fixed for the whole episode. Row order is fixed: hands, then the anchor obj1, then other objects, then PAD. Positions are z-scored by the dataset statistics; here those are computed per recording rather than over the training mix, so absolute values differ slightly from training while the structure does not. Why so much of the matrix is dead: the objects are static in the world and the reference frame is fixed per episode, so an object's entire pose_in_ref block is constant and only hand_in_entity moves — and that block is an affine function of the hand's own row (residual 1.9e-06), so it carries no independent information within a recording.
